Lektion 1 · End-to-End-Datenfluss

Vom Klick zur Datenbank – und sicher zurück

Du verfolgst genau eine Aktion: Die Turnierleitung trägt ein Matchergebnis ein. Danach kannst du erklären, welche Schicht welchen Teil der Arbeit übernimmt und warum eine schnelle zweite Eingabe nicht verloren geht.

Dauer
ca. 15 Minuten
Vorwissen
React-Grundlagen
Gewinn
einen Request verfolgen

Das mentale Modell

Cockpit, Schiedsrichter, Spielbericht

Die Analogie trennt drei Verantwortungen. Sie ist absichtlich grob; gleich danach verbinden wir sie mit den echten Modulen.

1

React ist das Cockpit

Es zeigt Eingaben sofort, hält vorläufigen Zustand und übersetzt Klicks in Nutzerabsichten. Es ist schnell, aber nicht die dauerhafte Wahrheit.

2

Der Worker ist der Schiedsrichter

Er prüft Sitzung, CSRF, Datenform und Fachregeln. Ein manipulierter Browser kann diese Regeln nicht umgehen.

3

D1 ist der Spielbericht

Erst was dort erfolgreich geschrieben wurde, überlebt Neuladen, Gerätewechsel und das Ende der aktuellen React-Sitzung.

Merksatz Der Client darf optimistisch arbeiten. Der Worker entscheidet, was erlaubt ist. D1 hält fest, was wirklich passiert ist.

2 · useRoundResults übernimmt den Entwurf

Absicht → Zustandsübergang → Autosave

Der Hook übersetzt die Änderung in eine Reducer-Action. Ein Effekt sucht anschließend Einträge, die gültig und dirty sind. Erst dann wird ein unveränderlicher Snapshot versendet.

use-round-results.ts Zeilen 187–214, 238–242 
if (
  validateScore(entry.draft) !== "valid" ||
  entryPersistence(entry) !== "dirty" ||
  entry.saving
) continue;

const snapshot = entry.draft;
dispatch({ type: "save-started", matchId: entry.matchId, token, snapshot, generation });
void mutate("/admin/matches/" + entry.matchId + "/result", {
  method: "PUT",
  body: JSON.stringify({
    teamAGames: snapshot.teamA,
    teamBGames: snapshot.teamB,
  }),
});

const change = useCallback(
  (matchId, team, games) =>
    dispatch({ type: "score-changed", matchId, team, games }),
  [],
);

3 · EventAdmin verbindet Schreiben und Neuladen

Fachmodul → Transportadapter

Das Ergebnis-Modul bekommt keine direkte Fetch-Abhängigkeit. Es ruft mutate(path, init) auf. Der Adapter sendet die Mutation, lädt danach das vollständige Event und vereinheitlicht Fehleranzeige.

EventAdmin.tsx Zeilen 145–162 
const mutate = useCallback(
  async (path: string, init: RequestInit) => {
    setError("");
    try {
      await api(path, init);
      await load();
    } catch (cause) {
      const failure = cause as Error;
      setError(failure.message);
      throw failure;
    }
  },
  [load, setError],
);

const roundResults = useRoundResults({
  round: data?.currentRound ?? null,
  mutate,
});

4 · api() baut die HTTP-Anfrage

Browserlogik → HTTP-Grenze

Alle Aufrufe erhalten das Präfix /api und JSON-Header. Bei schreibenden Methoden ergänzt der Helfer den aktuellen CSRF-Token. Fehlerantworten werden zu normalen JavaScript-Fehlern.

src/lib/api.ts Zeilen 11–21 
export async function api<T>(
  path: string,
  init: RequestInit = {},
): Promise<T> {
  const response = await fetch(`/api${path}`, {
    ...init,
    headers: {
      "content-type": "application/json",
      ...(csrfToken && !["GET", "HEAD"].includes(init.method ?? "GET")
        ? { "x-csrf-token": csrfToken }
        : {}),
      ...init.headers,
    },
  });
  // Antwort auswerten …
}

5 · requireAdmin schützt den Schreibvorgang

HTTP-Anfrage → Sicherheitsgrenze

Das HttpOnly-Cookie beweist eine gültige Sitzung. Für schreibende Methoden muss zusätzlich der Headerwert zum CSRF-Wert der Sitzung passen. Erst dann ruft next() den Routen-Handler auf.

worker/auth.ts Zeilen 45–60 
const session = await readSession(
  getCookie(c, "sga_session"),
  c.env.SESSION_SECRET,
);
if (!session) return c.json({ error: "Nicht angemeldet." }, 401);
if (
  !["GET", "HEAD"].includes(c.req.method) &&
  c.req.header("x-csrf-token") !== session.csrf
) {
  return c.json({ error: "Die Sitzung konnte nicht bestätigt werden." }, 403);
}
await next();

6 · Zod und Fachregel prüfen das Ergebnis

Unbekanntes JSON → gültige Fachdaten

TypeScript schützt nur Code beim Entwickeln; eine HTTP-Anfrage bleibt zur Laufzeit nicht vertrauenswürdig. Zod erzwingt ganze, nicht negative Zahlen. Die Route lehnt zusätzlich ein Unentschieden ab.

worker/index.ts Zeilen 489–500 
admin.put("/matches/:id/result", async (c) => {
  const input = z
    .object({
      teamAGames: z.coerce.number().int().min(0),
      teamBGames: z.coerce.number().int().min(0),
    })
    .safeParse(await c.req.json().catch(() => ({})));

  if (!input.success || input.data.teamAGames === input.data.teamBGames)
    return c.json(
      { error: "Ein gespieltes Match darf nicht unentschieden enden." },
      400,
    );
  // …
});

7 · D1 speichert die dauerhafte Wahrheit

geprüfte Fachdaten → SQL

Die Route prüft zuerst, ob das Match existiert. Danach fragt sie die gemeinsame Runden-Policy, ob dieser Zustand Ergebnisänderungen erlaubt. Erst dann bindet sie die Werte getrennt an ein vorbereitetes SQL-Statement und markiert das Ergebnis als gespielt.

worker/index.ts Zeilen 506–520 
if (!match) return c.json({ error: "Match nicht gefunden." }, 404);
if (getRoundPolicy(match.state).resultAccess === "closed")
  return c.json(
    { error: "Dieses Ergebnis kann im aktuellen Rundenstatus nicht geändert werden." },
    409,
  );

await c.env.DB.prepare(
  "UPDATE matches SET team_a_games = ?, team_b_games = ?, result_type = 'played' WHERE id = ?",
)
  .bind(input.data.teamAGames, input.data.teamBGames, c.req.param("id"))
  .run();
return c.json({ ok: true });

8 · Der Client lädt den bestätigten Stand

D1 → EventData → React

Nach dem erfolgreichen PUT wartet mutate auf load(). Die GET-Route baut aus D1 ein vollständiges EventData. setData(next) löst das erneute Rendern mit der Serverwahrheit aus.

EventAdmin.tsx Zeilen 134–150 
const load = useCallback(async () => {
  try {
    const next = await api<EventData>(`/admin/events/${id}`);
    setData(next);
    setDuration(next.event.default_round_duration_seconds / 60);
  } catch (cause) {
    const failure = cause as Error;
    setError(failure.message);
    throw failure;
  }
}, [id, setData, setDuration, setError]);

await api(path, init);
await load();

Der entscheidende Unterschied

Entwurf ist nicht gleich gespeicherter Stand

Ein einzelnes Match besitzt während der Eingabe mehrere Wahrheiten mit unterschiedlichen Aufgaben. Diese Trennung verhindert verlorene Eingaben und falsche Erfolgsmeldungen.

Wert Bedeutung Beispiel
draft Neueste Eingabe, die gerade in der UI sichtbar ist. 6:4
saving.snapshot Exakt der Stand, der zum laufenden Request gehört. 6:3
persisted Zuletzt erfolgreich vom Server bestätigter Stand. 6:3
failedKey Fehlgeschlagener Stand, der nicht endlos erneut gesendet wird. 6:3
Warum nicht einfach nur einen Spielstand speichern? Weil eine Serverantwort immer den Stand bestätigt, der vor einigen Millisekunden versendet wurde – nicht automatisch die neueste Eingabe, die inzwischen im Browser steht.

Unterwegs6 : 3unverändert
